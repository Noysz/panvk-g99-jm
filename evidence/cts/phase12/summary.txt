Phase 12 memory: lazy device-local memory, kbase heap size, memory
profile, FourFectVK device name (patch 0070), 2026-10-07

Root cause of the RAM growth in games (measured with PANVK_MEM_PROF):
  1. kbase backed every page of a VkDeviceMemory at vkAllocateMemory.
     DXVK 2.3.1 allocates device-local memory in 256 MB chunks and
     host-visible memory in 64 MB chunks, so RAM jumped by a whole chunk
     even when the chunk was almost empty (AIO Showcase: 272 MB allocated,
     6 MB used, DXVK HUD "Vidmem heap 0").
  2. The heap was reported as 75 % of RAM (5.63 GB). DXVK frees empty
     chunks only above 80 % of the heap, which a phone never reaches, and
     games size textures from DXGI DedicatedVideoMemory (= heap size).
  3. No driver leak: BO count, command pool cache (2-32 MB depending on
     the scene) and tiler/poly heaps stay flat over 90-186 s runs of the
     0.0.10 driver (aio_mem/v0.0.10_base_*).

Changes (0070):
  - device-local, not host-visible, not exported allocations >= 8 MB get
    kbase commit 0 + BASE_MEM_GROW_ON_GPF (pages on first GPU use);
    off: PANVK_KBASE_DEVMEM_EAGER=1, threshold PANVK_KBASE_DEVMEM_LAZY_MIN_KB.
    A CPU map of such a BO commits the full size first.
  - kbase heap = RAM / 3, clamped to [2 GiB, 75 % of RAM]: 2.50 GiB on an
    8 GB G99 phone (was 5.63 GiB); override PANVK_KBASE_HEAP_PERCENT=N.
  - PANVK_MEM_PROF=1|<file>: one line every 2 s (kbase BOs, VkDeviceMemory,
    lazy backed size, command pool cache, heaps, RSS, MemAvailable).
  - deviceName gets " FourFectVK <version>" from meta.json "name" or the
    install folder name; off: PANVK_NO_FOURFECT_NAME=1.
